When I start a screen, I skip the version with perfect data. I sketch the ones nobody screenshots first:

- **Empty**, before anything exists
- **Loading**, while the request is still out
- **Error**, when it comes back wrong
- **Too much**, when a name runs forty characters and the list has three hundred rows

These decide the layout more than the happy path does. A list that looks right with five items can fall apart with zero, or with five hundred. A title that fits on one line on my screen will wrap on someone's phone.

## A small example

A toast I built recently started this way. The happy path was fine. But the toast with an action only announced "undo" to a screen reader, without saying what would be undone. The fix was a better label, something like `aria-label="undo archive"`, not a redesign.

> The hard states are where people decide whether to trust what you built.

## How I work through them

Every component I build gets a small set of fake data next to it: an empty array, a promise that never resolves, one that throws, and a string that is far too long. I switch between them while I work, so the edge cases are there from the first commit instead of the week before launch.

It is slower for the first hour. It is faster for everything after.
